# Описание

Нефункциональные требования:

- RTO (время восстановления) = 45мин
- RPO (точка восстановления) = 15мин
- Одинаковое время загрузки страниц для пользователей из разных регионов


1. Приложение решено развернуть в трех зонах доступности (AZ) одного региона с использованием распределенного Kubernetes-кластера («растянутый кластер»). Такое решение оптимально благодаря следующим причинам:

   - Управление одним control plane снижает сложность администрирования и сокращает эксплуатационные затраты.
   - Репликация данных между зонами доступна быстрее, чем запросы между разными регионами, обеспечивая стабильную работу приложения в пределах одного региона.
   - Равномерная производительность сайта достигается благодаря использованию CDN, обеспечивающей одинаковые задержки загрузки для пользователей независимо от географического положения.

2. Внешний балансировщик нагрузки (Load Balancer) равномерно распределяет нагрузку между зонами доступности, перенаправляет трафик пользователям в зависимости от состояния служб и ограничивает чрезмерный объем запросов (Rate Limiting).

3. Принята активная схема отказоустойчивости (active-active failover), позволяющая поддерживать доступность приложений даже при сбоях отдельных зон.

4. Для обеспечения надежности хранения данных выбран инструмент Patroni, управляющий кластером PostgreSQL. Патрони обеспечивает автоматизацию процессов резервирования и переключения на резервные узлы при авариях, поддерживая высокую доступность данных.

5. Разделение данных на сегменты (шардирование) признано излишним ввиду небольшого объема хранимых данных (около 50 ГБ).
